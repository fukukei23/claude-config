# make-guide — ガイド系作成のディスパッチャ（振り分け）

## トリガーワード
「ガイド作って」「教科書作って」「チートシート作って」「語彙帳作って」「チュートリアル作って」「/make-guide」

## 目的
ユーザーは「読む系ガイド」と「引く系チートシート」の違いも「既存に追記か新規作成か」も覚えなくてよい。
既存ガイドの横断スキャン（add/new判定）と読む系/引く系の判定をLLMが行い、**必ず1回確認を挟んで**から適切なスキル（guide-builder / textbook-guide）に分岐する。
本スキル自体はガイドを生成しない（スキャン・判定・確認・分岐のみ。生成は各スキルに任せる）。

## フロー

### STEP 1: 内容の把握
直前の会話文脈から「作りたい内容」を把握する。
（ユーザーは会話の中で「これ残したい」と思って「作って」と言うことが多い。文脈が不足する場合のみ「何について作りますか？」と1回だけ聞く。）

### STEP 1.5: 既存ガイドスキャン（add / new 判定・2026-08-20追加）

作りたい内容と**テーマが重複する既存ガイドがないか、必ず機械的に検索してから**次へ進む（「被りはなさそう」という記憶・楽観でのスキップ禁止・検証回避バイアス対策）。

**検索方法（3ソース・日英両キーワードで）**:

```bash
# ① 公開一覧（guides repo・49+冊のhref一覧）
grep -oP 'href="[^"]+"' ~/projects/guides/index.html | sort -u
ls ~/projects/guides/ | grep -v -E '\.(html|md)$'
# ② SSOT一覧（カテゴリ別・外部独立サイト含む）
sed -n '/ガイドサイト/,/^## インフラ/p' ~/projects/obsidian-ssot/00_SYSTEM/全体マップ_MOC.md
# ③ 内容レベルの被り確認（テーマの日本語+英語キーワードで）
grep -rli "<キーワードja>\|<キーワードen>" --include="*.html" ~/projects/guides/ | head
```

⚠️ ①のhref一覧とlsで**ズレがあることがある**（実ディレクトリがあるのに一覧未掲載等）。両方見る。

**判定**:
- **テーマが完全一致する既存ガイドがある** → **add**（既存ガイドへの章追加・追記を優先提案）
- **部分被りしかない**（例: 1章ぶんの話題が既存ガイドに含まれるが、ガイド全体のテーマは違う） → **new + 相互リンク**（無理に章を足すと既存ガイドの焦点がぼやけるため）
- **被りなし** → **new**

判定結果は STEP 3 の確認に含めて提示する（addの場合は対象ガイド名も）。

### STEP 2: 読む系 / 引く系 の判定
内容から下表で判定する:

| 読む系 → guide-builder | 引く系 → textbook-guide |
|---|---|
| 手順を順に学ぶ・通読する | 必要な時に引く・検索する |
| 体系的・複数ページ構成 | 一覧・早見表・単一HTML |
| 例: 「Claude Codeの使い方全体」「Docker入門」 | 例: 「Gitコマンド一覧」「regex早見表」「用語集」 |

### STEP 3: 確認（必須・1回必ず挟む）

**判定に確信がある場合:**
> 「これは【add（既存『〇〇ガイド』に追記）/ new（新規作成）】×【読む系 / 引く系】ですね。【guide-builder(add) / guide-builder(new) / textbook-guide(new) 等】で進めてよろしいですか？」

**判定に迷う場合**（例: 「Gitのガイド」は読む系にも引く系にもなる）:
両者のメリット/デメリット＋おすすめを提示して選択:

```
この内容は読む系にも引く系にもできます。

📖 読む系（guide-builder・複数ページ）
  メリット: 手順を最初から学べる・体系立つ
  デメリット: さっと引けない

📋 引く系（textbook-guide・単一HTML）
  メリット: 必要な時にすぐ引ける・コンパクト
  デメリット: 通読には向かない

おすすめ: 【〇〇系】（理由: 〜）
どちらにしますか？
```

### STEP 4: 分岐
ユーザーが承認したら、対応するスキルを呼び出す:
- **読む系** → `guide-builder`（add判定なら既存ガイド名・章追加内容を引き渡す / new判定なら新規作成文脈を引き渡す）
- **引く系** → `textbook-guide`

ユーザーが「いや、こっちで」と言ったら、即そちらに分岐（再確認は不要）。

## 注意
- **必ず1回は確認を挟む**（誤判定防止・ユーザーの提案の核心）
- **STEP 1.5 のスキャンは省略不可**（「被りはなさそう」という楽観判断でのスキップは検証回避バイアス・add/newは機械検索の結果でのみ判定）
- make-guide 自体はHTMLを生成しない。スキャン・判定・確認・分岐のみ。
- 会話文脈がない場合のみ「何について作りますか？」と聞く（それ以外は聞き直さない）。
- 分岐先のスキルが index.html / 全体マップのN冊更新まで面倒を見る（本スキルは関与しない）。
- 分岐先 textbook-guide の「STEP 2: 既存ガイドスキャン→相互リンク選択」との役割分担: make-guideが「add/newの振り分け」を決め、分岐先は相互リンク選択等の詳細を担う（二重実行ではない）。
