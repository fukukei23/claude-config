# トラブルシューティング

Claude CodeのDesktop AppとCLI（WSL2）における設定・認証・ルーティングの問題解決ガイド。

> **最終更新: 2026-05-29**

---

## 前提: 2つの環境は完全に独立している

```
C:\Users\USER\.claude\           ← デスクトップアプリが読む（Windows側）
~/.claude/  (WSL2)               ← Claude Code CLI が読む（WSL2側）
```

この2つは**別々のディレクトリ**であり、設定は共有されない。

---

## デスクトップアプリの動作（チャット・Cowork・Codeタブ全て）

### 認証の仕組み
デスクトップアプリは `C:\Users\USER\.claude\.credentials.json` のAnthropicOAuthトークンを使う。
**OAuthが存在する限り、全タブがAnthropicのSonnetに向く。変更不可。**

```json
// C:\Users\USER\.claude\.credentials.json
{
  "claudeAiOauth": {
    "accessToken": "sk-ant-oat01-...",
    "subscriptionType": "pro"
  }
}
```

### settings.json のenvセクションについて
- OAuthが存在する場合、`C:\Users\USER\.claude\settings.json` の `env` セクションは**無効**
- envセクションにBASE_URLやAPIキーを書いても使われない

### ~/.bashrc に書いても意味がない
- `echo $ANTHROPIC_BASE_URL` でURLが変わって見えても、それはシェルの表示のみ
- デスクトップアプリのAPIコールには影響しない

### .credentials.json を削除するとどうなるか
- アプリ再起動時にOAuth再認証が走り、**自動的に再作成される**
- 削除では解決しない

### 結論
デスクトップアプリでベースモデルを変更する方法は現時点で存在しない。
ただし、MCPツール（`minimax_ask`, `glm_ask`）経由で外部LLMに処理を委譲できる。
Anthropic Proサブスクリプションを使い続けるのが現実的。

## Cursor Claude Code CLI の動作（WSL2内）

### 認証の仕組み
CursorでClaude Code CLIを起動した場合、WSL2の `~/.claude/settings.json` を読む。
**settings.jsonのenvセクションが有効で、.credentials.jsonより優先される。**

```json
// ~/.claude/settings.json (WSL2)
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://api.z.ai/api/anthropic",
    "ANTHROPIC_AUTH_TOKEN": "GLMのAPIキー",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "GLM-5.1"
  }
}
```

これにより GLM-5.1 / Z.AI を使える（2026-03-31 Cursorで動作確認済み）。

## Desktop MCP「Could not attach」エラー — protocolVersion不一致（2026-05-10）

### 症状
デスクトップアプリ起動時に「Could not attach to MCP server glm/minimax」が表示される。

### 原因の特定方法
`%APPDATA%\Claude\logs\main.log` を確認する：
```
Failed to connect to glm: Server's protocol version is not supported: 2025-11-05
```
このエラーが出ていれば protocolVersion 不一致が原因。

### 修正1: secrets.envのパス（HOME解決の問題）
Windows経由でWSL2スクリプトを実行すると `~` が `C:\Users\<user>` に解決される。
```diff
# ~/.claude/scripts/start-glm-mcp.sh / start-minimax-mcp.sh
- source ~/.secrets.env
+ source /home/yn4416/.secrets.env
```

### 修正2: protocolVersion（CLI ≠ Desktop問題）
CLIは `2025-11-05` をサポートするが、Desktopアプリ（v1.6608）は `2024-11-05` のみ。
```diff
# glm-mcp-server.py / minimax-mcp-server.py
- "protocolVersion": "2025-11-05"
+ "protocolVersion": "2024-11-05"
```

```bash
# 一括修正コマンド
sed -i 's/"protocolVersion": "2025-11-05"/"protocolVersion": "2024-11-05"/g' \
  ~/.claude/scripts/glm-mcp-server.py \
  ~/.claude/scripts/minimax-mcp-server.py
```

### 教訓
- Desktop向けMCPスクリプトは **`protocolVersion: "2024-11-05"`** 固定で管理する
- MCP接続失敗時の最初の調査先は `%APPDATA%\Claude\logs\main.log`
```

## CLI版: glm-rate-proxy トラブルシューティング

### プロキシバイパス問題（2026-05-28 発生・解決済み）

#### 症状
プロキシステータスAPIは `peak_block: true` / `provider: minimax` を返すが、実際のAPI使用量を見るとZAI（GLM）に直結している。`request_count` が 0 のまま。

#### 原因
`sync-secrets-to-settings.sh` が `.secrets.env` のZAI直結URLで `settings.json` を上書きし、プロキシURL（`http://127.0.0.1:8787`）を上書きしてしまう。

#### 確認方法
```bash
# プロキシのステータス確認
curl -s http://127.0.0.1:8787/proxy/status | python3 -m json.tool
# → request_count が 0 ならバイパス中

# 現在のBASE_URL確認
echo $ANTHROPIC_BASE_URL
# → https://api.z.ai/... なら直結（バイパス）
# → http://127.0.0.1:8787 ならプロキシ経由（正常）
```

#### 修正
`sync-secrets-to-settings.sh` の `source` 直後にプロキシ生存チェックを追加:
- プロキシ生存 → `ANTHROPIC_BASE_URL` を `http://127.0.0.1:8787` に上書き
- プロキシ死亡 → `.secrets.env` の直結URLをそのまま使用（安全なフォールバック）

### ピークブロックが効かない場合

1. **プロキシが起動しているか**: `pgrep -f "python3 -m glm_rate_proxy"`
2. **BASE_URLがプロキシ向きか**: `echo $ANTHROPIC_BASE_URL`（`http://127.0.0.1:8787` であること）
3. **ピーク時間設定**: `cat ~/.config/glm-rate-proxy/config.json` の `peak_hours` 確認
4. **環境変数で無効化されていないか**: `echo $GLM_PEAK_BLOCK`（`false` なら無効）

### プロキシが起動しない

1. `cat /tmp/glm-proxy.log` でログ確認
2. `PYTHONPATH=src python3 -m glm_rate_proxy` で手動起動してエラー確認
3. ポート競合: `lsof -i :8787`
4. ImportError: `pip3 install aiohttp`
5. 起動失敗時は `settings.json` がZAI直結URLに自動フォールバック

### セッション途中でプロキシが死んだ場合

```bash
# 再起動
pkill -f glm_rate_proxy; sleep 1
cd ~/.claude/scripts/glm-rate-proxy && PYTHONPATH=src nohup python3 -m glm_rate_proxy > /tmp/glm-proxy.log 2>&1 &
sleep 2
curl -sf http://127.0.0.1:8787/proxy/status
```

### エラー時フォールバックが動かない

- プロキシの `_handle_upstream_error` が 500/502/タイムアウト/接続エラー時にMiniMaxに自動フォールバックする仕組み
- MiniMax APIキーが設定されていない場合はフォールバック不可
- MiniMaxもエラーの場合は 503 が返る
