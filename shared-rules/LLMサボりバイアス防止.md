# LLMサボりバイアス防止（共通）

## 核心（厳格）
LLM（ホスト自身を含む）は「省略方向・楽観・迎合・検証回避」にサボる。**語彙検知・自己申告は無効**（偽答リスク・3機レビューで否定）。**構造化出力で思考を外部化**し、**機械的検証**で封じる。

## 実行前チェック（構造化出力・省略不可・2026-07-26 Phase0）
Edit / Write / 破壊的Bash（rm/sed -i/>/git push/git reset --hard 等）の前・および重要設計判断時に以下を**出力**する（自己申告「やりました」でなく形式で強制・ホストがspot check可能）:
- **反証シナリオ1つ**: この変更/判断で壊れうるケース
- **最悪ケース3つ**: 想定外の影響
- **固有事情**: 対象コード行番号 or 関数名（一般論禁止）
- **省略デメリット**: 「既存で足りる」とする場合は省くことの代償1つ

※ 読み系（ls/grep/cat/Read）は対象外（alert fatigue回避）。

## 検証宣言の形式（a′・2026-08-28 5層設計Phase0）

「検証済み/確認済み/合格/PASS」と書く各ケースには、**走らせるまで貼れないもの**を含む4点セットを必須とする（形式要求が行動を駆動・実装者=検証者の検証範囲選択の偏り対策）:

- **(a) 実行コマンド (b) 生exit code（既存「生exit code添付」と同一） (c) 観測出力の生ログ引用 (d) 不合格閾値の定義**（どうなったらfailか）
  - **閾値は事前固定の参照値と突合して設定**（「exit code 0-255ならOK」等の恒真閾値禁止・spec v2）
  - **引用は実際に実行した結果のコピー**であること（環境指紋 `[fp:時刻/l1=キャッシュ行サイズ]` suffix推奨・LLM自己生成テキストやecho捏造は無効）
- **fail条件ケースを1つ以上含める**: 一番壊れうる経路を自ら選んで検証する（「検証した範囲」の選択偏り対策・2026-08-28偽陰性テスト型の再発防止）。未実施ケースが残るなら「合格（限定条件: <条件>）」と条件を明示
- 破壊的failケース（rm系・本番操作等）は「対象外」と明示して良い（気軽に走らせられないため）
- **バックログ起票時も「fail条件」を先行記入**（空欄なら警告のみ・強制しない）（c層・`type:verification`ラベル推奨）

## 完了宣言の効果-証跡対応ゲート（2026-08-17 追加・検証の対象ズレ対策）

「✅完了/修正完了」を言う前に:
1. **最終効果を1文で定義する**（何がどうなれば「完了」か）
2. **その効果を直接確認した実測証跡**（コマンドと出力・対象件数）を提示する
3. 手元の証拠が中間指標（テスト合格・Lint・ビルド成功）だけなら「**実装済み・効果未確認**」とだけ言う——完了とは言わない
4. 完了条件が運用上の効果なら、**効果を1コマンドで実測する道具**（--explain 等）を変更とセットで作る

### 適用拡張: 原因を断定する時も同ゲートを通す（2026-08-26 追加・診断局面の空白を塞ぐ）

**原因・真因を述べる時は、先頭に必ずラベルを付ける**:

- **【実測】** — そう言える**コマンドと出力を併記する**。併記できないなら【実測】と書いてはいけない（語彙検知でなく**形式の強制**）
- **【仮説】** — 未実測。SSOT記録に書く時は frontmatter に `hypothesis: true` と該当項目を明記する

**なぜ必要か**: 既存3ゲート（実行前チェック=Edit/Write直前・効果-証跡ゲート=完了宣言直前・生exit code添付=成功宣言直前）は「**行動の前**」と「**完了の後**」しか守っておらず、**その間の『原因を特定する局面』が空白**だった。

経緯: 2026-08-25 の1セッション内で診断局面の断定ミスが**3回連続**。①`fork: Resource temporarily unavailable` を未実測のまま「メモリ枯渇」と断定 → 実測で否定（available 43GB・`ulimit -u` 190,881）②grep の「0件」を鵜呑み → 実際はパス二重変換で**検索自体が壊れていた** ③「ZAI残高が有力」と推測を記録に書く → **別セッションが事実として引き継ぎ、日記の「未解決」欄に昇格**。③は語尾に「（未確定）」と書いても**伝播を止められなかった**実証であり、語尾注記では不十分＝ラベル/フィールドで縛る必要がある根拠。

## 検索結果を事実として使う前の確認（2026-08-22 追加・同型2回発生）

**`grep` / `Grep` ツール / `ls` の「件数」や「0件」を根拠に結論を出す前に、必ず中身を目視する。**

検索が返す件数は「検索が正しく機能した」ことを意味しない。**パターンが壊れていても、パスが解決できなくても、結果は静かに「0件」や「N件」として返る**。これを検証せず結論にすると、誤った事実が下流（バックログ・他LLMへのレビュー依頼・設計判断）へ伝播する。

- **0件だった時**: 「存在しない」と結論する前に、**検索が機能したことを別の方法で1回確認する**（対象ファイルを直接 Read する／確実にヒットするはずの語で試し撃ちする）。特に **Grep ツールに WSL パスを渡すと機能せず 0 件を返すことがある**（2026-08-22 実測）
- **N件だった時**: 件数だけで語らず、**`-o` でなく実際の行を数行出力して目視する**。正規表現が意図通り解釈されているか確認する
- **シェル経由の正規表現は特に危険**: `grep -oE "...\*\*\*..."` のようにクォート内でエスケープすると、シェル処理で `\*` が `*` に落ち、ERE で「直前要素の0回以上」に化ける。`{4}*` は「4文字がゼロ回以上」＝**空文字にもマッチする**（2026-08-22 これで「先頭4文字が5箇所漏洩」と誤判定し、実際は0件だった）
- **報告に件数を書く時**: その数字を出したコマンドと、**中身を目視した証跡**をセットで示す

経緯: 2026-08-22 の1セッション内で同型のミスが2回発生（①`sanitize-settings` の参照元を「0件＝孤立スクリプト」と誤断定、実際は Stop hook から毎セッション呼ばれていた ②壊れた正規表現で「先頭4文字が5箇所 GitHub に漏洩」と誤断定、実際は完全マスクで漏洩ゼロ）。②は**誤情報のまま3機レビューに渡り、2機が critical 指摘を返す**ところまで波及した。該当は13類型の「自信過剰（ダブルチェック怠る）」「検証回避（未テストで確認済と言う）」。

## 完了報告への「生 exit code 添付」義務化（2026-08-23 L22 追加）

**完了報告で「成功した」「動いた」「テスト PASS」と書く前に、対象コマンド自身の exit code をそのまま出力した生テキストを必ず1回添付する。**

### なぜ生テキストか

パイプ `| tail` / `| head` / `| grep` / `| sed` を挟むと **添付が物理的に不可能**になる。形式が強制されることで誤読が構造的に弾かれる。

```bash
# ✅ 正しい: 終了コードがそのまま見える
$ bash ~/bin/ssot-auto-sync.sh 2>&1; echo "EXIT=$?"
[2026-08-23 15:39:06] [auto-sync] ...
15:39:45 synced
EXIT=0

# � 誤り: tail の終了コード（常時0）を見てしまう
$ python3 job.py | tail -20; echo "EXIT=$?"
...出力...
EXIT=0  # ← job.py が timeout で死んでも EXIT=0
```

### 必須ルール

1. **完了報告に「対象コマンド自身の exit code をそのまま出力した生テキスト」を添付する**
   - `; echo "EXIT=$?"` を末尾に付ける（パイプ無しで実行する）
   - または `set -o pipefail` を有効にしてから実行し、その旨も併記
2. **`| tail` / `| head` / `| grep` を末尾に挟まない**（挟むなら `set -o pipefail` 必須）
3. **`if cmd | grep ...; then` パターン禁止**（grep の終了コードを見てしまう）
4. **「成功した」「動いた」「テスト PASS」と書く前に、上記の生テキストを1回は出力したか確認する**
5. **`timeout` で殺された処理**は特に注意 — exit 124 を出すが、`tail` 経由だと 0 に見える

### `set -o pipefail` の標準化

完了報告用のコマンド実行では原則 `set -o pipefail` を有効にする:

```bash
set -o pipefail
bash ~/bin/ssot-auto-sync.sh 2>&1; echo "EXIT=$?"
```

これでパイプラインの **いずれかのコマンドが失敗** したら全体が非0になる。`tail` で隠蔽されない。

### 破った直近事例（2026-08-23 同日1セッション内2回）

1. **`if git diff | grep | head -10; then 警告`** — `head` の常時0を見て「機密0件」と誤警告。実際は機密あり
2. **`python3 job.py | tail -20; echo EXIT=$?`** — `tail` の終了コードを見て「完了」と誤報告。実際は timeout で殺されていた

→ 層1ルール「検索結果を事実として使う前の確認」は毎セッション読まれているのに**2回とも防げなかった**。本セクションで「**形式が強制される（`| tail` を挟めない）ことで構造的に防ぐ**」アプローチに切り替える（3機レビューで Gemini・MiniMax・GLM が一致して critical/high 指摘）。
