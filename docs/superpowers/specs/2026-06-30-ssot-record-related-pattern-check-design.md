# ssot-record「関連パターンチェック（フェーズ1.5）」設計

## 背景・課題

2026-06-30のセッションで、以下の2つの問題を別々の`brainstorming`セッションとして解決した:

1. Windows Desktop版Claude CodeのBashツールがWSLパス（`~/projects/...`）を解決できない問題（path-rewriteフック実装）
2. Windows Desktop版から`git push`が`Permission denied (publickey)`で失敗する問題（HTTPS+gh CLI方式で解決）

どちらも実は根本原因が同一だった（Windows DesktopとWSL2は別ホームディレクトリを持つ別OSであるため、ファイルパスもSSH鍵も互いから見えない）。しかしこの繋がりに気づいたのはユーザーであり、Claude（私）は自発的に統合しなかった。

調査の結果、2つの異なる失敗ポイントが判明した:

1. **Claude自身の統合判断の欠如**: 1つ目の問題を解決した後、2つ目に着手する際に「これは同じ構造の問題では」と立ち止まって確認するステップが、作業フローのどこにも存在しなかった
2. **`ssot-record`スキルの構造的な設計の欠落**: フェーズ1（分類判定）は、渡された「記録する内容」というテキスト1件だけを見て単発の振り分け先を機械的に判定する仕組みで、「今日の他の記録と根本原因を共有していないか」という横断的なパターン認識のステップが一切ない

本specは2番目（`ssot-record`の構造的欠落）に対応する。1番目（Claudeの自発的な気づき）は本specの範囲外（プロセス・習慣の問題であり、ツールでの強制は別途検討）。

## 採用設計: フェーズ1.5「本日含む過去7日の関連パターンチェック」

既存の`ssot-record`スキルの**フェーズ1（分類判定）の直後・フェーズ2（確認画面）の前**に新フェーズを挿入する。フェーズ1で`project`が確定して初めて、どの`_INDEX.md`を見るべきか分かるため、この位置にする。

### 処理内容

1. フェーズ1で確定した`project`の`01_DECISIONS/<project>/_INDEX.md`を読む（既存の1行サマリーをそのまま使う・追加読込なし）
2. ファイル名の日付（`YYYY-MM-DD_<内容>.md`形式）が**過去7日以内**（当日含む）のエントリだけを候補として抽出する
3. 各候補ファイルのfrontmatterから`tags:`を軽量grepで取得し、今回つけるタグ（フェーズ1の判定結果）との**重なり数**を計算する。これはフィルタには使わず、次のLLM判定への補強材料として渡す
4. 稼働中のLLM（WSL CLI版=自分自身で直接判定／Windows Desktop版=glm/minimax MCP経由。フェーズ1と同じ割り当てルールに従う）に、「今回の記録内容」と「候補エントリの要約＋タグ重なり数」を渡し、**根本原因・構造的パターンが共通していないか**を意味的に判定させる
5. 関連ありと判定された場合のみ、フェーズ2の確認画面に以下の追加ブロックを出す:
   ```
   🔗 関連パターン検知（過去7日・同一プロジェクト内）
   「<候補エントリ名>」と根本原因が共通する可能性があります
   （理由: <LLM判定理由1行>・共通タグ: #xxx #yyy）
   構造的な文書への追記も検討しますか？[y/N]
   ```
6. `y`の場合: 追記先を決め打ちせず「この洞察はどこに書くのが適切だと思いますか？（既存ドキュメント名 or『なし』）」とユーザーに一言確認し、回答をフェーズ3のファイル作成・更新タスクに追加タスクとして組み込む
7. `N`または関連なしの場合は何もせず通常のフェーズ2へ進む（追加ブロックなし）

### 設計判断の理由

- **同一プロジェクトのみ（他プロジェクト横断は対象外）**: インフラ・ツール層の根本原因（今回のWindows/WSL問題）は`claude-code`プロジェクトの記録内で完結しており、`reserve-optimizer`や`atelier-kyo-manager`等のビジネスロジック寄りのプロジェクトと根本原因が一致するケースは稀。全プロジェクト横断は20リポジトリ分の`_INDEX.md`を毎回読むコスト・ノイズに見合わない
- **過去7日（当日のみではない）**: ユーザーの作業パターンが数日にまたがることが多いため、当日限定では拾いきれないケースがある
- **タグはフィルタでなく補強材料**: 今回の実例（path-rewriteフック=`#claude-code #hook #WSL #Windows-Desktop`、GitHub認証=`#claude-code #git #ssh #Windows-Desktop #github-cli`）はタグが2つ重なっていたが、機械的フィルタだけでは見落とした実績がある（実際に見落としたのはClaude自身の判断ステップの欠如によるもので、タグ重なりを参照する仕組み自体が無かったため）。タグはLLM判定の確からしさを上げる補助情報として渡し、最終判断はLLMの意味比較に委ねる
- **自動では書かない・提示と確認のみ**: 誤判定時に勝手に文書を書き換える事故を防ぐため。`y`の場合も追記先をユーザーに確認してから実行する
- **追記先を決め打ちしない**: `01_基礎概念.md`は`claude-code-guide`固有の存在で、他プロジェクトには対応物がない場合がある。プロジェクトごとに適切な「構造的文書」は異なるため、毎回ユーザーに確認する設計にする

### 残るスコープ外の事項（このspecでは扱わない）

- Claude自身が複数のbrainstormingセッションをまたいで自発的に「これは同じ問題では」と気づくための行動変容・習慣化は、本specの範囲外（ツールでの強制ではなくプロセス上の課題）
- 全プロジェクト横断チェックは扱わない（採用しない判断として上記に明記）
- `_INDEX.md`が存在しないプロジェクト（新規プロジェクト等）でのフォールバック挙動は、plan策定時に詳細化する（候補なし＝関連パターンなしとして扱う想定）

## テスト方針（plan策定時に詳細化）

- 今回の実例（path-rewriteフック→GitHub認証問題）を過去ログとして再現し、2件目の記録時にフェーズ1.5が1件目を関連パターンとして検知することを確認
- 無関係な記録（例: 別プロジェクトの単発バグ修正）でフェーズ1.5が誤検知しない（何も提示しない）ことを確認
- `_INDEX.md`に過去7日以内のエントリが0件の場合、フェーズ1.5が何も提示せず正常にフェーズ2へ進むことを確認
- `_INDEX.md`が存在しないプロジェクトでの挙動を確認
