# ssot-record「関連パターンチェック」設計

## 背景・課題

2026-06-30のセッションで、以下の2つの問題を別々の`brainstorming`セッションとして解決した:

1. Windows Desktop版Claude CodeのBashツールがWSLパス（`~/projects/...`）を解決できない問題（path-rewriteフック実装）
2. Windows Desktop版から`git push`が`Permission denied (publickey)`で失敗する問題（HTTPS+gh CLI方式で解決）

どちらも実は根本原因が同一だった（Windows DesktopとWSL2は別ホームディレクトリを持つ別OSであるため、ファイルパスもSSH鍵も互いから見えない）。しかしこの繋がりに気づいたのはユーザーであり、Claude（私）は自発的に統合しなかった。

調査の結果、2つの異なる失敗ポイントが判明した:

1. **Claude自身の統合判断の欠如**: 1つ目の問題を解決した後、2つ目に着手する際に「これは同じ構造の問題では」と立ち止まって確認するステップが、作業フローのどこにも存在しなかった
2. **`ssot-record`スキルの構造的な設計の欠落**: フェーズ1（分類判定）は、渡された「記録する内容」というテキスト1件だけを見て単発の振り分け先を機械的に判定する仕組みで、「過去の他の記録と根本原因を共有していないか」という横断的なパターン認識のステップが一切ない

本specは2番目（`ssot-record`の構造的欠落）に対応する。1番目（Claudeの自発的な気づき）は本specの範囲外（プロセス・習慣の問題であり、ツールでの強制は別途検討）。

## MiniMaxレビューを経た設計の見直し

初稿（フェーズ1の後に新フェーズ1.5を追加し、同一プロジェクトのみを過去7日分チェック）をMiniMaxにレビューさせたところ、以下の重大な指摘を受けた:

1. **`_INDEX.md`の1行サマリーには「症状」しか書かれておらず「根本原因」が書かれていないことが多い**。タグ重なりとLLM意味比較だけで判定させても、症状レベルの記述からは今回のような根本原因の一致を見抜けない可能性が高い（今回の見落としと同質の脆さ）
2. **フェーズ1の分類判定と別にLLM呼び出しを追加すると、コスト・レイテンシが増える**。フェーズ1の既存LLM呼び出しに統合すれば追加コストなしで同等の効果を得られる
3. **「同一プロジェクトのみ」は不十分**。インフラ・ツール層の根本原因（例: 今回のWindows/WSL分離）は、`claude-code`以外の個人開発プロジェクトでも同じ症状で再発しうる

これらを踏まえ、ユーザーとの追加協議の上で設計を改訂した。さらに改訂版をGLM・MiniMaxの双方に再レビューさせたところ、両者が独立に同じ2点を指摘した:

4. **`root_cause`を「任意」のままにすると、結局書かれないエントリが大半になり、当初の問題（症状しか書かれない）が再発する**
5. **grepによる日付抽出はファイルパス中の数字や日付フォーマットの揺れで誤爆しやすい**。frontmatterのような構造化フィールドを対象にすべき

この2点も以下の最終設計に反映した。

## 採用設計

### 1. フレームワーク: フェーズ1への統合（独立フェーズ1.5は廃止）

MiniMaxの指摘2を採用し、新しいLLM呼び出しを追加するのではなく、**既存フェーズ1（分類判定）のプロンプトを拡張**して、分類と同時に関連パターン判定もさせる。

処理の流れ:

1. **（新規・LLM呼び出しなし）候補収集**: フェーズ1のLLM呼び出しの**前**に、`01_DECISIONS/*/<YYYY-MM-DD_*.md>`の**frontmatterの`date:`行**を対象に、過去7日以内（当日含む）のものを`grep`で抽出する（後述「日付抽出の方式」参照。ファイル名やパス文字列は対象にしない）
2. 抽出した候補（プロジェクト名・対応する`_INDEX.md`の1行サマリー・後述の`root_cause`）を、フェーズ1の既存LLM呼び出しのプロンプトに追加コンテキストとして含める。プロンプトには**「これらの過去ログは`related_pattern`の判定にのみ使い、`project`/`tags`等の通常の分類判定には使わないこと」「無関係な場合は迷わず`related_pattern: null`を返すこと」を明示**し、過剰検出（false positive）を抑制する
3. フェーズ1のJSON出力スキーマに新フィールド`related_pattern`を追加する（`project`/`tags`等の既存フィールドの後ろに配置し、分類への影響を避ける）:
   ```json
   "related_pattern": null
   ```
   または
   ```json
   "related_pattern": {
     "entry": "01_DECISIONS/claude-code/2026-06-30_Windows-Desktop版WSLパス変換フック実装.md",
     "reason": "Windows DesktopとWSL2が別ホームディレクトリを持つことに起因する点で根本原因が共通",
     "common_tags": ["claude-code", "Windows-Desktop"]
   }
   ```
4. フェーズ2の確認画面で、`related_pattern`が非nullの場合のみ追加ブロックを表示:
   ```
   🔗 関連パターン検知（過去7日横断）
   「<related_pattern.entry>」と根本原因が共通する可能性があります
   （理由: <related_pattern.reason>・共通タグ: #xxx #yyy）
   構造的な文書への追記も検討しますか？[y/N]
   ```
5. `y`の場合: 追記先を決め打ちせず「この洞察はどこに書くのが適切だと思いますか？（既存ドキュメント名 or『なし』）」とユーザーに一言確認し、回答をフェーズ3のファイル作成・更新タスクに追加タスクとして組み込む
6. `N`または`related_pattern`がnullの場合は何もせず通常のフェーズ2へ進む

この統合により、**追加のLLM呼び出しは発生しない**（MiniMaxの指摘2に対応）。

### 2. 範囲: 全プロジェクト横断だが「過去7日以内に動きがあったプロジェクト」に限定

MiniMaxの指摘3（同一プロジェクトのみでは不十分）を受け、当初の「同一プロジェクトのみ」から方針転換した。ただし全24プロジェクトの`_INDEX.md`（実測: 合計1956行）を毎回フルで読むのはコストに見合わないため、以下の2段階で絞り込む:

1. `grep`で全`01_DECISIONS/*/YYYY-MM-DD_*.md`から**frontmatterの`date:`行**を対象に、過去7日以内（当日含む）のものを抽出する（後述「日付抽出の方式」参照）
2. 該当したファイルが属するプロジェクトの`_INDEX.md`から、対応する1行サマリーを取得する

この時点で候補が存在するプロジェクトは、実測上ユーザーが直近1週間に実際に活動した数プロジェクト程度に絞られる（24プロジェクト全部が毎週動いているわけではない）。

#### 日付抽出の方式（GLM/MiniMaxレビューを反映）

当初案の「ファイル名や`_INDEX.md`本文を対象に日付パターンをgrepする」方式は、以下の理由で**frontmatterの`date:`行を対象にする方式**に変更する:

- ファイルパスやディレクトリ名に偶然日付に似た数字列が含まれていると誤爆する
- `_INDEX.md`の1行サマリー本文は自由記述のため、日付フォーマットが揺れうる
- 一方、`01_DECISIONS/<project>/YYYY-MM-DD_<内容>.md`のfrontmatターには既存フォーマットで`date: YYYY-MM-DD`が必ず1行存在するため、これだけを対象にすれば構造的に確実に抽出できる

実装は`grep -r "^date: " 01_DECISIONS/*/*.md`のように、frontmatterの`date:`行のみを対象にした単純なテキスト抽出にする（シェルの`date`コマンドによる日数計算と組み合わせ、複雑な正規表現は避ける）。

### 3. `root_cause` frontmatterフィールドの新設・構造化（GLM/MiniMaxレビューを反映し必須寄りに変更）

`01_DECISIONS/<project>/YYYY-MM-DD_<内容>.md`のfrontmatterに`root_cause`フィールドを追加する。当初「任意・自由記述」としていたが、GLM・MiniMax双方から「任意のままでは結局書かれないエントリが大半になり、当初の問題が再発する」と指摘されたため、**選択式カテゴリ＋`unknown`許容**の構造に変更し、実質的に毎回値を埋める運用にする:

```yaml
---
project: claude-code
date: 2026-06-30
tags: [claude-code, git, ssh, Windows-Desktop, github-cli]
root_cause:
  category: design_mismatch
  description: Windows DesktopとWSL2は別ホームディレクトリを持つ別OSである
---
```

- `category`は固定の選択肢から選ぶ: `code_defect`（コード上の不具合） / `design_mismatch`（設計・前提のズレ） / `requirement_change`（要件変更） / `external_dependency`（外部要因） / `operational_error`（運用ミス） / `unknown`（不明・特定できない）
- **`unknown`を許容することで「無理に断定しない」自由度を残しつつ、フィールド自体は省略させない**（カテゴリ選択というLLMにとって負荷の低いタスクにすることで記入率を確保する）
- `description`は1行の自由記述。`category`が`unknown`の場合は空でもよい
- フェーズ1の候補収集時、`root_cause`が存在するエントリ（特に`unknown`以外）はLLMへの判定材料として優先的に使う
- 既存の過去エントリへの遡及適用（バックフィル）は本specのスコープ外とする（過去資産の一括改修は別途検討）

### 4. タグは判定の補強材料（変更なし）

当初設計を維持。タグ重なりはフィルタとして使わず、LLM（フェーズ1拡張プロンプト内）への補強情報として渡す。

### 5. 自動では書かない・提示と確認のみ（変更なし）

誤判定時に勝手に文書を書き換える事故を防ぐため。`y`の場合も追記先をユーザーに確認してから実行する。追記先を決め打ちしないのも当初設計通り（プロジェクトごとに適切な「構造的文書」が異なるため）。

### 6. 失敗時・冪等性の扱い

- **grep候補収集が失敗、または該当0件の場合**: `related_pattern: null`として通常通り進める（フェーズ1全体を失敗させない。既存の`check-command-safety.py`等と同じ「エラー時は処理を止めない」方針に揃える）
- **フェーズ1のLLM呼び出し自体が失敗した場合**: 既存の「LLMがJSONを返さなかった場合」のフォールバック処理（正規表現抽出→それも失敗ならClaude自身がデフォルト判定）にそのまま従う。`related_pattern`は無理に判定せずnull扱いとする
- **冪等性**: 候補収集は「既にコミット済みのエントリ」のみを対象にする。今回新規作成中のエントリ自体はまだファイルとして存在しないため、自己参照によるループは発生しない
- **同日内に複数回`ssot-record`を呼ぶ場合**（MiniMaxレビューで指摘）: 1回目の記録が既にコミットされていれば、2回目の候補収集時にそれが対象に入るのは意図通りの挙動（むしろ今回のセッションで実際に起きたケースそのもの）。問題になるのは「コミット前の中間状態」を誤って拾うことだが、候補収集はコミット済みファイルのみを`grep`するため、未コミットの作業中ファイルを誤って拾うことはない

### 7. `related_pattern`判定結果の保存（MiniMaxの指摘を受けて新規追加）

判定のたびに同じ比較を再計算するコストと、関連性が記録に残らず陳腐化するのを防ぐため、`related_pattern`が非nullだった場合、**新規作成するファイルのfrontmatterに`related_entries`として保存する**:

```yaml
---
project: claude-code
date: 2026-06-30
tags: [claude-code, git, ssh, Windows-Desktop, github-cli]
root_cause:
  category: design_mismatch
  description: Windows DesktopとWSL2は別ホームディレクトリを持つ別OSである
related_entries:
  - 01_DECISIONS/claude-code/2026-06-30_Windows-Desktop版WSLパス変換フック実装.md
---
```

- 双方向リンク（関連先エントリ側にも逆参照を書き込む）は本specのスコープ外とする。まずは新規エントリ側からの片方向リンクのみとし、運用上必要性が高まれば別途検討する
- この保存により、将来同じ2エントリ間の関連性を再度LLMに判定させずに参照できる

## 残るスコープ外の事項（このspecでは扱わない）

- Claude自身が複数のbrainstormingセッションをまたいで自発的に「これは同じ問題では」と気づくための行動変容・習慣化は、本specの範囲外（ツールでの強制ではなくプロセス上の課題）
- 既存の過去エントリへの`root_cause`遡及バックフィルは扱わない
- 「過去7日」固定窓の妥当性（週末をまたぐ場合の取りこぼし等）はplan策定時にさらに検討してよいが、本specでは7日固定を採用する（MiniMaxは「直近N日 OR 直近M件の多い方」を提案したが、まずはシンプルな7日固定で運用し、実際に取りこぼしが発生したら調整する）

## テスト方針（plan策定時に詳細化）

- 今回の実例（path-rewriteフック→GitHub認証問題、同一プロジェクトclaude-code）を過去ログとして再現し、2件目の記録時にフェーズ1の拡張プロンプトが1件目を`related_pattern`として検知することを確認
- 異なるプロジェクトにまたがる関連パターン（例: インフラ層の問題が別プロジェクトでも記録されているケース）を人工的に作り、横断検知が機能することを確認
- 無関係な記録（例: 別プロジェクトの単発バグ修正）で誤検知しない（`related_pattern: null`になる）ことを確認。特に「日付が近いだけで内容は無関係」なケースで過剰検出（false positive）しないことを重点確認する
- 過去7日以内のエントリが全プロジェクトで0件の場合、grep候補収集が空になり正常に`related_pattern: null`で進むことを確認
- `root_cause`がカテゴリ選択式で正しく記入される（`unknown`を含む）ことを確認。明確な根本原因がない記録でも`category: unknown`としてフィールド自体は省略されないことを確認
- フェーズ1への`related_pattern`フィールド追加が、既存の`project`/`tags`等の分類精度に悪影響を与えていないことを確認（統合前後で同一の記録内容に対する分類結果を比較する）
- ファイルパスや本文中に日付に似た数字列が含まれるケースで、frontmatterの`date:`行のみが対象になり誤爆しないことを確認
- `related_entries`がfrontmatterに正しく保存されることを確認
