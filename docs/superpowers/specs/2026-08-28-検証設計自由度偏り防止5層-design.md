## 1. 問題定義（不変構造）

**検証の設計には自由度があり（何ケースで試すか・どの経路で試すか）、その自由度が常に「成功を示す側」に偏る。実装者と検証者が同一LLMエージェントである限り、不合格になる構成を自発的には試さない。**

過去4事例で再発済み:
| 事例 | 自由度の偏り |
|---|---|
| pokeka (08-17) | ユニットテストという楽な検証手段を選び実効果を未検証 |
| grep誤報 (08-22) | 検出不能な使い方（壊れた正規表現・WSLパス）で「無し」と断定 |
| 診断断定3連発 (08-26) | 実測前に原因を断定 |
| 偽陰性テスト (08-28) | 層2が発火するファイル数・cwd一致位置で試し、回避構成（cwd不一致×≤10ファイル）を未試験のまま「合格」 |

既存防御（受入条件の事前登録・効果-証跡対応ゲート・生exit code添付・【実測】/【仮説】ラベル）は**すべて通過して「合格」に至った**。空白は「検証の網羅性の自己申告」を強制する形式の不在。

## 2. 設計概要（5層）

```
「検証した範囲だけで合格/完了宣言する」不変構造
├─ a′ 宣言形式+証跡紐付け（引用は実行結果のコピー→走らせるまで貼れない=形式が行動を駆動）
├─ b′ Stop hook機械差戻し（確定語×検証語の共起・差戻し回数state累積）
├─ c  計画時fail条件先行記入（バックログ起票テンプレ）
├─ d′ 3機レビュー強化（実装者外fail条件提案+集約ルール+/tmp固有名）
└─ e′ フェイルセーフ層（e′-lite: trap case+環境指紋 / medium: プロセス突合 / full: 月次人間監査）
```

各層が**異なる弱点**をカバーし、全層同時突破を困難にする（独立性の担保）。

## 3. 各層の仕様

### a′ 宣言形式+証跡紐付け（層1ルール+hook）
完了宣言で「検証済み」と書く各ケースに必須:
1. 実行コマンド
2. 生exit code
3. 観測出力の**生ログ引用**（セッション出力からのコピー）
4. そのケースで不合格になる観測値の**閾値定義**（**事前固定の参照値や既知failケースとの突合**で設定・「exit code 0-255ならOK」等の恒真閾値は不可【v2】）

hookは「実施済み」記載行の引用文字列が**transcriptのtool_result（ツール実行結果）側に実在するか**照合し、無い行は「未実施」扱い【v2: LLM自己生成テキスト・echo出力は照合対象外=偽ログ捏造を構造的に排除】。引用には環境指紋suffix `[fp:$(date +%s)/l1=$(getconf LEVEL1_DCACHE_LINESIZE)]` を必須化（e′-liteから前倒し・過去ログ流用を困難化）

**性質**: 引用は実行結果のコピーなので、実際にfailケースを走らせるまで貼れない→**形式要求が行動を駆動する**。

### b′ Stop hook差戻し（check-fail-coverage.sh・新設）
- **「検証系タスク」の操作的定義**: 完了宣言文に確定語と検証語が**共起**するもの（これ以外の定義は使わない・回避されたらPhase2で発火語を調整）
- 発火条件: 確定語（✅/完了/合格/PASS）×検証語（検証/テスト/実測/確認）の**共起**（単独では発火しない・誤検知抑制）
- 検査: a′の4要素（引用+閾値）の記載有無
- 差戻し: 1回目=再出力促進 / 2回目以降=state累積カウントで**実ユーザー入力ターン（transcript JSONLのユーザー発言・LLM生成テキストは不可）に承認文言が無い限り毎回block**【v2・3機critical一致: LLMが自分で「承認:」と書く循環を断つ】
- 構造: check-yagi-output.shと同型（transcript読み・1回差戻し・state管理）

### c バックログ起票テンプレ拡張
- 検証系タスクの起票時に「fail条件: 」列を先行記入 + **`type:verification` ラベル**を付与【v2: ラベル付きタスクはb′hookの検査対象（fail条件欄空欄チェック含む）・「空欄警告のみ」は形骸化するため】

### d′ multi-llm-review強化（SKILL.md改訂）
1. レビュー雛形に追加: 「(6) 実装者が挙げたfail条件以外のfail候補を最低1つ提案せよ（**実装者提示条件の言い換えでないこと**・独立した失敗経路を指すこと【v2】）」
2. 集約ルール明文化: **判定自体へのcritical/high指摘を却下して元判定を維持する時のみユーザー明示承認が必要**（採用して改訂する分には従来通り自動）
3. /tmp/req_*.json を**セッション固有suffix**（`_$(SESSION_ID先頭8桁)`）に標準化（08-28実再発の衝突事故対策・L27）

### e′ フェイルセーフ層（3段階）
- **e′-lite（Phase 2実装）**:
  - trap case: **週次**cronが「必ずfailするはずのケース」（壊れた正規表現のgrep等）を合成→hook+レビューがcatchできるか検知率を測定【v2: 月次→週次・検知遅れ短縮】
  - **hook設定ファイルのsha256整合チェック**: settings.jsonのhooks節+hookスクリプトのハッシュを週次trapで検証（LLMによるhook無効化・改変の即時検知【v2・3機critical】）
  - 環境指紋引用suffix: 引用文に `[fp:$(date +%s)/l1=$(getconf LEVEL1_DCACHE_LINESIZE)]` を必須化（同マシン・同タイミングでの事前実行が必要→過去ログ流用を物理的に困難化・**a′へ前倒し適用済み**）
- **e′-medium（別起票）**: PostToolUse logスキーマ拡張（実行コマンド+BASHPID記録）+引用と実行の同時性・因果性突合
- **e′-full（別起票）**: 月次人間サンプリング監査（無作為N件/月・hook/レビューすり抜け調査）

## 5. テスト方針（b′ hook・自害テスト5ケース）
1. 確定語+検証語の共起あり・a′要素なし → 差戻し
2. 共起あり・a′要素あり（引用実在） → 通過
3. 共起なし（確定語のみ） → 通過（非検証系）
4. 2回目差戻し後・承認文言なし → block継続
5. 実ユーザー入力ターンに承認文言あり → 通過
6. 共起あり・引用文字列がtool_result側に存在しない（偽引用） → 差戻し【v2】
7. 共起あり・引用は実在するが閾値と引用ログの値が算術不整合 → 差戻し【v2】
8. 共起あり・引用が古いセッション/assistant生成テキスト由来 → 差戻し【v2】

## 6. 既知の限界（4件・正直に明記）
1. **検出方法のトートロジー**（grep正規表現が壊れた0件）はa′で防げない → d′とユーザーのメタ認知に委ねる
2. **破壊的failケース**は気軽に走らせられない → a′対象外を明文化（削除系・本番系）
3. **都合の良い断片だけ引用** → e′-lite環境指紋で困難化+d′独立性で補完
4. **形式遵守は「嘘の品質」を上げるのみ**（検証の網羅性はd′の独立fail提案でのみ向上）

## 7. 反証シナリオ（本設計が誤りと分かる条件）
- Phase0-2実装後に「検証した範囲だけで完了宣言」パターンが再発した時（**測定: a′4要素+b′承認の全通過後に事後フォレンジックでfail相当が判明した件数≥1**【v2】）
- hookの誤検知率>50%で運用継続不能になった時
- 3機レビューのコストが検証系タスクの実施コストを超えた時
