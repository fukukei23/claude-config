# プロンプト: リポジトリ価値抽出分析

> **用途**: 既存リポジトリから独立再利用可能なコンポーネントを発見・評価するプロンプト
> **カテゴリ**: 評価系
> **前提**: Claude Code環境で実行。事前に `repo-deep-analysis.md` でリポジトリ全体を理解済みであることが推奨

---

以下のリポジトリの「価値抽出分析」を実行してください：`{{REPO_URL}}`

リポジトリ内の各モジュール・ファイルを精査し、**他のプロジェクトで独立して再利用可能なコンポーネント**を特定・評価してください。推測ではなく、実際のコードを読んだ事実のみを記述すること。

```markdown
# リポジトリ価値抽出レポート: [リポジトリ名]

## 1. 分析方針
- **分析観点**: 独立性（外部依存の少なさ）、独自性（代替品の有無）、完成度（品質・テスト）
- **評価基準**: 以下の3段階で評価
  - Tier 1（高価値）: 即座に抽出可能で代替品が少ない
  - Tier 2（中高価値）: 抽出にリファクタリングが必要だが独自性が高い
  - Tier 3（低〜中価値）: 抽出可能だが既存代替品が存在する

## 2. コンポーネント一覧

各コンポーネントについて以下の形式で評価：

### [コンポーネント名]
- **場所**: [ファイルパスとサイズ]
- **機能**: [何をするものか（具体的功能）]
- **外部依存**: [抽出を阻害する依存関係]
- **抽出難易度**: 低 / 中 / 高（理由付き）
- **独自性**: 高 / 中 / 低（代替品の有無と比較）
- **Tier**: 1 / 2 / 3

（以下、候補となるコンポーネントごとに繰り返し）

## 3. Tier別サマリ

### Tier 1: 高価値（即抽出推奨）
| コンポーネント | 場所 | 価値の理由 |
|---|---|---|
| ... | ... | ... |

### Tier 2: 中高価値（リファクタリング後に抽出）
| コンポーネント | 場所 | 必要な作業 |
|---|---|---|
| ... | ... | ... |

### Tier 3: 低〜中価値（必要に応じて）
| コンポーネント | 場所 | 備考 |
|---|---|---|
| ... | ... | ... |

## 4. 抽出推奨順位
1. **最優先**: [理由]
2. **次点**: [理由]
3. ...

## 5. 抽出時の注意点
- 共通して必要なリファクタリング
- ライセンス上の懸念
- パッケージ化の方向性（pip/npm/Docker等）
```

### ツール活用ガイドライン

1. **Glob**: 全ファイルのマッピング。特に `*.py`、`*.ts`、`*.js` などのロジックファイルを網羅
2. **Grep**: 再利用可能性の高いパターンを検出
   - クラス定義: `class.*:`
   - 公開API: `def |export |module.exports`
   - 設定/ファクトリ: `config|factory|builder|strategy`
   - エラーハンドリングパターン: `except|catch|fallback|retry`
3. **Read**: 候補ファイルの精読。特に `__init__.py`、`index.ts`、エクスポート定義で公開APIを把握
4. **Agent**: 複雑な依存関係グラフの追跡にサブエージェントを委譲
5. **Bash**: `wc -l`（行数）、`grep -r "import"`（依存抽出）、`grep -r "from"` で外部依存を機械的に調査

### 分析のポイント

- **「独立して動くか？」** を最重視。内部クラス/関数への依存が多いものは抽出困難
- **「npm/pip に代替品があるか？」** を必ず確認。車輪の再発明は価値が低い
- **「このコードを書くのに何時間かかるか？」** を基準に独自性を評価。数時間で書けるものより、数週間かかる知見が詰まったものを高く評価
- **テストの有無** も評価基準に含める。テスト済みコードは信頼性が高い
